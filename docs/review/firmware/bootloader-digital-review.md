# Implemented digital-only boot adapter: independent review

The implemented removal of full `DaisyPatchSM::Init` and audio transport from the DFU boot adapter is accepted for the bounded source and linked integration scope reviewed here. The previously omitted DCache disable was restored before the final reviewed rebuild. This is not a hardware or production qualification.

## Power and codec evidence

The official Patch SM v1.0.5 datasheet, printed page 2 / PDF page 5, explicitly permits USB-only partial power for firmware updates and says that the audio codec will not function properly in that condition. Its stray “Seed2 DFM” product names are verbatim in that paragraph. TI PCM3060 recommended operating conditions, page 2, require analog VCC 4.5–5.5 V. USB nominal 5 V through board input protection and the analog regulator cannot establish that minimum across all allowed supply/dropout conditions. The current Patch initializer calls `codec.Init(i2c2)` but ignores its result; codec register accesses have 250 ms I2C timeouts. It then starts ADC and DAC as well as the SAI transport used by main for LED/button callbacks. None of those analog functions supplies data to the bootloader.

This establishes an unsupported analog dependency and avoidable startup delay, not proof that every USB-only boot necessarily hangs: SAI A is configured as a clock master and might keep delivering DMA callbacks even with a failed codec. Digital-only initialization removes the dependency. It does not by itself certify USB current draw, digital rail margins, brownout behavior or the physical board.

Sources: https://daisy.nyc3.cdn.digitaloceanspaces.com/products/patch-sm/ES_Patch_SM_datasheet_v1.0.5.pdf and https://www.ti.com/lit/ds/symlink/pcm3060.pdf .

## Semantics that must be preserved

- Call unchanged `startup_process()` first. Its reset-mediated JUMP path and retained backup-SRAM commands must run before regular board initialization. Its default QSPI pin configuration exactly matches Patch: IS25LP064A, memory mapped, IO0 PF8, IO1 PF9, IO2 PF7, IO3 PF6, clock PF10, chip select PG6.
- Initialize the same patched System clock/SDRAM profile and QSPI before `boot.Init`; preserve PC7 LED. The independent core review owns SDRAM/clock correctness. Preserve the existing DCache-off policy before USB/DFU buffer work and the existing boot optimization setting.
- **Keep the invalid `Pin()` button argument.** `Bootloader::Init` then selects PG3, normal polarity, no pull. Passing a valid PG3 pin instead selects the default `Switch::Init(pin)` overload, which inverts the signal and enables a pull-up. That would regress the active-high hardware BOOT0 button with external pull-down.
- The old `Bootloader::AudioProcess` body only calls `ManageLed`, switch debounce and rising-edge state bookkeeping. The candidate factors that body exactly into public `ProcessControls`; `AudioProcess` remains a wrapper, while the new TIM5 callback calls `ProcessControls` directly. Exact string-transform equality against upstream verifies that no statement in the body or elsewhere in shared bootloader.cpp changed. The only header change is the new public declaration. This removes the proposed dependency on dummy/null audio buffer arguments.
- Preserve approximately 1 kHz independent interrupt cadence. The original Patch transport uses 48 samples at 48 kHz. `Switch::Debounce` additionally gates its shift register to at most one sample per millisecond using HAL ticks. A main-loop-only replacement could stall through filesystem/USB activity and stretch the roughly 7-sample rising-edge debounce. A timer interrupt is the appropriate replacement.
- **Use TIM5, not default TIM2 or raw TIM3/TIM4.** System owns TIM2. TIM3/TIM4 period is truncated to 16 bits by this TimerHandle implementation; TIM5 is 32 bits. Enable its IRQ and set callback after `boot.Init`, then start it before `boot.IoInit`, preserving the existing audio-start ordering.
- Set `Config.period = (2 * System::GetPClk1Freq()) / 1000 - 1` **before** `TimerHandle::Init`, with the profile's APB1 divide-by-2. Timer period is ARR+1. Boost nominal 478.4 MHz CPU gives 239.2 MHz timer clock and ARR 239199. LibDaisy enables ARR preload. Setting only `SetPeriod` after initialization at default UINT32_MAX can leave the first interval at the old maximal reload because that setter writes ARR without issuing an update event; HAL initialization issues UG using the original period. Derive rate from the live clock, rather than hard-code one profile's period. Revisit the multiplication assumption if TIMPRE or APB division changes.
- In the supplied deinit callback, fully `DeInit` the added timer before `System::DeInit`. Timer `Stop()` alone does not disable its IRQ; timer DeInit invokes the HAL MSP deinit that disables the peripheral clock and NVIC interrupt. Preserve shared DFU/flash/load and reset code.

## Remaining risks and bounded alternative

TIM5 interrupts use priority 15 in libDaisy. This differs from the original audio interrupt priority; sustained higher-priority work can delay LED/debounce service. The short callback and millisecond HAL gating make the approach reasonable, but simultaneous DFU/SD activity and real button timing need hardware qualification. An accidental 250 Hz cadence from a 16-bit timer or stale first ARR would be a meaningful regression. Merely invoking the callback from the main loop is a weaker alternative because the existing loop has synchronous filesystem work.

Removing analog initialization means boot mode no longer explicitly drives audio samples, starts CV DAC zero buffers or configures gate outputs low. Digital pins remain at reset states. This is intentional for a USB update adapter, but a Eurorack-powered boot and software-reset scenario must be checked for output transients and external amplifier behavior. Sending digital silence cannot guarantee a valid analog output on USB-only power anyway; the absence of initialized audio is not a claim of a qualified mute.

All seven shared files were compared to pinned upstream: only `bootloader.cpp/.h` differ, by the exact control-body factoring and public declaration described above. `dfu.cpp/.h`, `dfu_log.h`, `usbd_desc.c` and `usbd_dfu_if.h` remain byte-identical. Startup backup-SRAM commands, reset-mediated load path, DFU transport/USB descriptors, flash writes and timeout state machine are unchanged. Upstream references: https://github.com/electro-smith/DaisyBootloader/tree/8b279a8e25922b786c24a6cbd1d499cdc1e76934 and https://github.com/electro-smith/libDaisy/tree/08087203debc646d3710ec8caa35bac6cf20ab5e . Input hashes and the bounded final review checklist are in `bootloader-digital-review.json`.

Completed implementation checks: the successful crossbuild uses 107388 of 131072 FLASH bytes. Final ELF symbol inspection finds `StatusTick`, `DigitalDeInit`, `ProcessControls` and TIM5_IRQHandler, with no DaisyPatchSM, PCM3060, AudioHandle, SaiHandle, AdcHandle or DacHandle symbols. Disassembly of linked main confirms DCache CCR bit clearing and clean/invalidate barriers immediately after System initialization, before SDRAM, QSPI and boot/USB setup. The initial TIM5 ARR is 239199; the live APB clock is checked against exactly 239200000 Hz and fails closed otherwise. Callback installation precedes timer start, timer start precedes IoInit, and the deinit callback stops and fully deinitializes TIM5 before System. An explicit Stop followed by DeInit is redundant but valid with this HAL implementation. The default TIM2 System timer remains separate. Build warnings include the existing newlib syscall stubs and RWX load segment; a successful link is not a claim that every warning was removed.

Remaining physical qualification: USB-only and Eurorack-powered enumeration/download/reset; normal 2 s, skip 100 ms and infinite timeout behavior; held/released button, LED and simultaneous DFU/SD service timing; output transients and digital supply margin. The core agent separately owns the opt-in SDRAM/clock profile. Stock binaries, legacy memory handoffs and production compatibility are not accepted by this scoped review.
