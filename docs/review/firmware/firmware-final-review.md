# Final bounded firmware review

**PASS for source and linked prototype scope. Hardware tests remain unrun; production and stock-binary compatibility are not qualified.** This final review supersedes the rejected initial firmware candidate. It inspected the current six-file SDK change and three-file bootloader change, final linked artifacts and maps, actual gate ordering, clock/count calculations, public API surface, default-off code, profile selection and archive dependencies. No canonical source, CAD or build artifact was modified by this review.

All nine changed-source hashes, both patch hashes and all seven artifact hashes match the final manifest. Five linked ELF images (digital bootloader, FLASH/QSPI/internal-SRAM passthrough and memory test) independently contain COUNT369 at the HAL refresh write, the geometry guard, corrected PLL2 actual-register gates and RevV/fresh-controller rejection before clock initialization. The direct SDRAM guard precedes HAL_SDRAM_Init, which would otherwise clear the timer. Four startup HAL command results and refresh programming are checked. Default-off sdram, DaisyPatchSM and System machine code and relocations match pristine pinned upstream; complete SDK global defined symbols are unchanged and existing public headers are unchanged.

The corrected PLL1 uses integer M5/RGE1, N299 Boost and N249 Default, giving478.4/398.4MHz, with nominal frequency reported through existing clock-query APIs. PLL2 M3/N37/FRAC4096, P8/Q2/R1 keeps25/100/200MHz outputs and100MHz SDCLK while centering its reference in RGE2. PLL3/audio configuration remains unchanged. At the allocated+1000ppm upper frequency, the chosen CPU/VCO values remain below their applicable RevV limits. RevV is checked before attempting the new clock configuration. Source/register arithmetic validation cannot establish the crystal's actual frequency, load, drive, startup or thermal behavior.

COUNT369 correctly implements the32ms prototype target at the99.9MHz allocated lower clock, with20 scheduling cycles and literalCOUNT+1 accounting. It gives31.98078078ms including that allowance versus the RAM's64ms maximum. The host test passes17 invalid snapshots and7936 bounded arithmetic cases. Those tests are source/arithmetic evidence, not proof of hardware frequency or worst-case FMC command scheduling. The cache-controlled64MiB memory-test image is compiled and linked but has not run on a board.

The former stale-profile issue is closed for the documented0/1 workflow: a configuration stamp invalidates SDK objects when switching profiles, exact parsing rejects empty/multiword/invalid inputs, and application ELF dependencies include the SDK archive and linker script. A read-only make question reports profile1 up-to-date and profile0 requiring rebuild. Different application execution targets use separate build directories. Users must select the delivered SDK explicitly; an arbitrary stock/third-party archive is outside support. Concurrent conflicting profiles in one build directory remain unsupported.

The final bootloader initializes only System, SDRAM, QSPI and a1kHz TIM5 control callback. It no longer initializes audio/ADC/DAC. ProcessControls is an additive loader method factoring the old AudioProcess body; AudioProcess remains available. The reset/DFU/QSPI storage sequence is unchanged: loading records the backup JUMP marker, performs an actual system reset, and early startup jumps before a second bootloader hardware initialization. Application refresh programming therefore occurs once in a fresh controller epoch, rather than rewriting a live SDRTR. No self-refresh protocol was added. The loader now uses pinned libDaisy v9 instead of its upstream24be dependency, which is an explicit dependency upgrade.

Final bootloader FLASH is **107388/131072 bytes**, leaving **23684 bytes (18.07%)** with this exact toolchain/configuration. The earlier2040-byte headroom finding is superseded. Reviewed maps use the selected SDK, preserve region/address definitions and allocate zero SDRAM code/data in these examples. This fit does not certify other bootloader options or future library/compiler changes. Link warnings for unimplemented Newlib syscall stubs and RWX segments remain visible; no profile-specific arithmetic/compiler warning was found.

Supported prototype paths are standalone internal-flash startup and the selected patched official-v6 reset-mediated QSPI/internal-SRAM applications. Stack, vectors, C startup, constructors and code/data accesses must not depend on SDRAM before board initialization. Required physical conditions include RevV MCU, correct16MHz crystal circuitry, industrial RAM temperature through85°C, adequate supply/VCAP and timing/routing qualification. Unmodified stock binaries, legacy external-memory handoffs, SDRAM execution/early access, live second initialization, arbitrary active-memory clock changes and SDRAM retention across reset remain unsupported.

Two documented software limits remain: unchanged TimerHandle microsecond conversion has nominal GetUs bias about+0.08368% Boost/+0.10050% Default (and correspondingly short delays), so exact wall-clock equivalence is not claimed; upstream boot IoInit discards several inner USB/SD initialization results, so checking its top-level result is not comprehensive error propagation. The prototype's fail-fast claim is limited to its explicit clock/FMC state, SDRAM command, QSPI and timer checks. Hardware USB/SD/boot/reset/audio integration and loaded full-memory/temperature/supply testing remain required.

The acceptance is limited to **refresh calculation, guarded initialization and digital boot/app integration**, not a qualification of every FMC/SDRAM memory timing. The timing fields must be decoded through the actual HAL register write and RM0433 p875, not multiplied directly as API literals: HAL writes SelfRefreshTime4 as TRAS field3; RM maps TRAS0 to2cycles, so the documented decode is5cycles/50ns, above ISSI-6 tRAS42ns. The shortcut4×10ns=40ns is therefore not a justified defect finding. In contrast, TXSR7 decodes to7cycles/70ns, exactly the ISSI70ns minimum; at the allocated+1000ppm SDCLK it would be69.9301ns. Self-refresh/clock-transition paths are explicitly unsupported here and require a separately corrected timing profile before enabling them. This is an analytical configuration boundary, not merely an unspecified bench-test concern. Normal-transfer/read sampling, shortest-cycle jitter and command timing still need a complete manufacturer/controller/board budget before a first-article or production freeze.
